# 容器资源隔离与超卖机制

## 问题

容器规格里的 "2C4G" 到底是什么意思？一台物理机上能跑多少个这样的容器？为什么 CPU 可以超卖而内存超卖有 OOM 风险？

## 简答

容器通过 cgroups 做资源限额、namespace 做环境隔离。"2C4G" 是配额上限而非独占：CPU 是分时调度配额，内存是硬上限。CPU 可以超卖是因为它能分时复用，内存超卖则可能触发 OOM。

## 综合结论

### 1. 容器不是虚拟机

容器和虚拟机的隔离级别不同：

| | 虚拟机 | 容器 |
| --- | --- | --- |
| 隔离层 | 硬件级（Hypervisor） | 进程级（共享宿主机内核） |
| 内核 | 每个 VM 独立内核 | 共享宿主机内核 |
| CPU | vCPU，独占或分时 | cgroups CFS 调度配额 |
| 内存 | 预留固定物理内存 | cgroups memory 限额，按需分配 |
| 启动速度 | 秒级到分钟级 | 毫秒级到秒级 |

容器一旦被调度到某个节点，就绑定在该节点上运行，直到生命周期结束。容器不支持热迁移，消失的方式是销毁而非迁移。

### 2. "2C4G" 的真实含义

**CPU（2C = 2000 milli）**：

- 不是独占 2 个物理核心。
- 是 cgroups CFS（Completely Fair Scheduler）配额：在每个调度周期（通常 100ms）内，容器最多使用 200ms 的 CPU 时间。
- 相当于"最多能用 2 个核心的算力"，但实际跑在哪些物理核心上由内核调度器决定，可能在多个核心间漂移。

**内存（4G）**：

- 是硬上限：容器最多使用 4GB 物理内存。
- 不是预留：不用的时候不占物理内存，用多少占多少，到 4GB 就触发 OOM Kill。

### 3. 超卖：CPU 和内存的本质区别

| 资源 | 能否超卖 | 原因 | 超卖后果 |
| --- | --- | --- | --- |
| CPU | 可以，通常 3-5 倍 | CPU 是分时复用的，大部分容器大部分时间不在计算 | 响应变慢，不会 crash |
| 内存 | 风险高，通常 1.0-1.5 倍 | 内存是实际占用的，不能分时 | OOM Kill 容器 |

关键区分：**limit 超卖 ≠ 实际使用超卖**。

即使所有容器的 memory limit 总和超过物理内存，只要实际使用量不超，就不会 OOM。CPU 同理：limit 总和可以远超物理核心数，只要任意时刻实际计算的容器不多，就不会有性能问题。

风险场景是大量容器同时高负载：实际 CPU 或内存使用超过物理资源，CPU 表现为变慢，内存则触发 OOM。

### 4. OOM 的两层机制

**容器级 OOM**：单个容器的内存使用超过其 cgroups memory limit。

- 只杀这个容器，不影响其他容器。
- 是容器隔离的基本保障。

**全局 OOM**：所有容器的实际内存使用总和超过物理内存。

- 内核 OOM Killer 介入，按 oom_score 选择进程杀掉。
- 可能波及无辜容器。

成熟的容器平台通过以下方式降低全局 OOM 概率：

- 调度时预留内存 buffer，不把节点塞满。
- 按实际使用率的 P95/P99 估算调度密度，而非简单按 limit 求和。
- 节点内存到水位线后停止调度新容器。
- QoS 等级（Guaranteed / Burstable / BestEffort），OOM 时先杀低优先级容器。

### 5. 对业务的影响

- 容器被 OOM Kill 后，本地文件系统数据丢失，需要重建。
- 持久化数据应放在外部存储（对象存储、网络文件系统等），不依赖容器本地磁盘。
- 业务侧应通过探活机制检测容器是否可用，不可用时自动重建。

## 未决问题

- 不同容器运行时（containerd、CRI-O）在 OOM 处理上的具体差异。
- 异构资源（GPU、高带宽网络）的超卖策略。
