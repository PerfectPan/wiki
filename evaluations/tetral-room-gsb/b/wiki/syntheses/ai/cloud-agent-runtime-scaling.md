# 云端 Agent 的规模化架构：把 runtime 移出沙箱

## 问题

当 Agent 从本地单机运行走向云端多租户服务时，直接把完整的 Agent 循环塞进虚拟机或容器沙箱，为什么会导致系统在扩展性、安全性和容灾恢复上面临瓶颈？如何解耦各个组件的职责，才能支撑大规模并发会话与长时间运行的复杂任务？

## 简答

计算机应当是 Agent 调用的外部资源，而不是 Agent 运行的宿主环境。将包含模型调用与状态推演的运行时（runtime）移出沙箱，变成无状态、可随时替换的纯计算节点；借助预写日志（WAL）协议在外部数据库完成状态提交后再发起实际操作，同时把沙箱解耦为按需延迟分配的易失执行资源。这种解耦让系统容量不再受制于虚拟机调度瓶颈，并实现了跨节点崩溃恢复与凭据完全隔离。

## 综合结论

### 1. 核心矛盾：为什么把 Agent 捆绑在沙箱里无法规模化

本地编码 Agent（如 Claude Code 或 Codex CLI）最初设计为安装在单台计算机上的程序，直接依赖本机的终端、文件系统和工具。早期云端方案（如 Manus、Anoma）为了复现这一体验，直接将整个 Agent 循环整体放进虚拟机沙箱（如 E2B）中运行。

这种「沙箱即 Agent」的捆绑模式在规模化时暴露出三个根本性冲突：

- **资源扩展曲线冲突**：Agent 核心逻辑是稳定的服务计算，状态可以长久保留并在多个工作阶段间复用；而沙箱是高频创建、销毁且具有强隔离要求的突发执行环境。容器与虚拟机编排系统（如 Kubernetes Pod 或 microVM 控制平面）在面对超高频的沙箱调度和回收时，序列化调度与启动延迟会迅速成为全局瓶颈。
- **状态持久化与故障恢复断裂**：如果会话历史、执行轨迹和未消费的中间状态全部保存在沙箱实例的内存或本地磁盘中，沙箱一旦重启或异常退出，整个任务上下文便彻底丢失；而为了排查异常，工程团队又不得不直接访问包含用户私有代码和数据的沙箱，造成隐私泄漏风险。
- **凭据泄露风险**：如果 Agent 在沙箱内部运行，为了请求大模型或访问外部服务，系统必须把模型服务商的 API 密钥或用户的 OAuth 凭据注入沙箱。恶意代码或提示词注入攻击一旦突破沙箱防线，就会直接窃取底层凭据。

### 2. 职责解耦：移出沙箱后的分层架构

解决上述冲突的途径是界定运行时的边界：所有具备不同所有者、不同生命周期或不同扩展特性的职责，全部移出执行容器，归入专门的服务组件。

| 组件 | 部署形态与职责 | 核心控制机制 |
| --- | --- | --- |
| **Runtime（运行时）** | 无状态计算节点，承载会话与线程的状态机演进（纯计算 Reducer） | 仅在内存中基于已提交事实推导下一步动作，不直接发起数据库写操作或外部网络调用 |
| **Bridge（状态桥接）** | 状态提交与事务协调服务，连接运行时与持久化存储 | 校验请求所属权与顺序序号，以单事务原子提交状态变更、幂等操作回执与任务队列事件 |
| **PostgreSQL（事实存储）** | 权威数据源，存储不可变执行事件流与上下文投影 | `session_events` 保存全部执行流，`session_messages` 保存模型上下文投影，`session_bridge_operations` 保存幂等回执 |
| **Gateway（模型网关）** | 无状态凭据与协议代理层 | 验证运行时的临时所有权令牌，在代理请求时动态注入凭据；明文密钥永不进入运行时与沙箱 |
| **Queue（异步队列）** | 基于数据库发件箱（Outbox）模式的任务投递系统 | 负责消息重试、顺序保证、租约超时与死信管理；搭配 `pg_notify` 与定时轮询发现机制 |
| **Sandbox Service（沙箱服务）** | 独立管理 Linux、macOS、Windows 等执行环境生命周期 | 按需延迟分配实例，将环境初始化、文件载入与具体命令执行拆解为独立任务 |

### 3. 可靠性保证：执行前预写协议（Write Ahead of Execution）

当运行时成为随时可能被重新调度的无状态节点时，核心难题在于：一旦宿主节点崩溃，替补节点如何判定某一步外部操作是尚未开始、正在执行还是已经完成。

架构借鉴了数据库预写日志（WAL）的核心原则：**任何能够推进任务状态或产生外部副作用的操作，必须在实际分发执行之前，先完成持久化提交。**

- **声明提交**：运行时推导出下一步需要调用外部能力（如运行一条终端命令）时，必须先向 Bridge 提交一个带有全局唯一幂等标识的不可变声明。
- **原子入库**：Bridge 校验会话所属权与执行序号，在同一个数据库事务中记录状态变更并生成操作回执。只有收到数据库确认后，运行时才被允许对外发起调用。
- **崩溃恢复与防重**：当网络波动导致应答丢失，或者运行时节点意外退出时，替补节点重新向 Bridge 提交相同标识的声明，Bridge 会直接返回已有回执而不会创建重复操作；新节点只需从数据库拉取已提交的事件与上下文投影，交由状态机重新推导即可继续前进，完全无需恢复已丢失的进程内存。

### 4. 权限与审批：独立审核线程与双阶段判定

隔离凭据只能解决「非受信环境拿不到明文密钥」的问题，无法判断「当前这一步工具调用是否符合安全策略」。

将运行时移出沙箱后，外部调用必须在发出前经过独立的检查流程：

1. **第一阶段策略判定**：模型提出工具调用请求后，运行时先将其传入策略规则引擎。如果该工具配置了必须审核策略（例如敏感的系统写入或网络操作），系统不会立即生成可执行的任务，也不会下发给沙箱，而是将其标记为待审核提案。
2. **派生独立审核任务**：系统基于该提案的上下文计算确定性标识，派生出一个独立的审核线程。审核线程接收提案内容、模型上下文以及安全策略要求，作为证据进行推导。需要注意的是，外部输入可能夹带提示词注入内容，因此安全策略定义严格由平台持有，与待审素材物理分离。
3. **决策落盘与第二阶段放行**：审核结果（允许、拒绝或降级人工介入）必须先经由 Bridge 写入数据库事务。随后规则引擎执行第二阶段判定，唯有拿到持久化的放行记录后，系统才会生成对外公开的工具调用事件，并正式投递给沙箱服务。遇到节点崩溃或超时等不确定情况，默认判定为失败，严禁将未确认状态作为放行依据。

### 5. 双维度扩展模型：会话与线程

为了让复杂的长时间任务高效推进，系统在组织结构上将上下文隔离和资源共享解耦为两个正交维度：

- **横向扩展：会话（Session）与工作区（Workspace）**：
  - 工作区容纳长期的静态资源，例如代码仓库、共享文件、记忆存储以及环境凭据配置。
  - 多个并行的业务场景（例如一个负责新功能实现、一个负责文档编写、一个负责架构审计）分别建立为独立的会话。各个会话独立推进自身的生命周期与事件流，互不干扰，仅在最终阶段将经过验证的产物合并回工作区。
- **纵向扩展：线程（Thread）与子任务**：
  - 会话内部如果需要执行并发探索，不能在单条上下文里并发请求模型（否则会导致上下文序号竞争和状态分叉），而是派生出相互独立的子线程。
  - 父线程通过明确的派生规则指定子线程可见的历史范围（例如完全不带历史、携带全部上下文或仅保留最近数轮），子线程运行在完全隔离的上下文空间中。
  - 父子线程之间的交互完全视同外部输入，通过异步队列有序投递，杜绝跨线程直接修改彼此上下文的情况。

## 具体运转案例：一条 Bash 命令的执行链路

以 Agent 在执行任务时需要运行一段系统命令为例，展示各解耦组件如何配合：

```text
[用户输入] 
   │
   ▼ (事务写入事件、Inbox 与 Queue 任务，API 返回 200)
[PostgreSQL / Queue]
   │
   ▼ (Job Runner 依序投递)
[Runtime Pod (无状态)] ── 状态机推导 ──> 产生 Bash 提案
   │
   ▼ (第一阶段：Bridge 事务提交工具调用声明 agent.tool_use 与 Queue 任务)
[PostgreSQL]
   │
   ▼ (未就绪时进入激活流程)
[Sandbox Service] ── 延迟启动沙箱 / 挂载文件 ──> 运行命令 ──> 暂存未消费结果
   │
   ▼
[Runtime Pod] ── 获取结果 ──> 提交 agent.tool_result 声明
   │
   ▼ (Bridge 事务写入结果、更新上下文、标记消费并出具回执)
[PostgreSQL]
   │
   ▼ (确认提交)
[Runtime Pod] ── 状态机继续推导下一步
```

1. **输入投递**：用户通过外部接口发送指令，系统在单笔数据库事务中完成事件记录、线程收件箱登记与队列任务创建，随后即可立即响应。队列工作组件按线程严格保序，将消息投递至负责该会话的运行时节点。
2. **命令声明与事务提交**：运行时中的状态机分析输入，生成 Bash 执行提案。在向外部发出命令前，运行时向 Bridge 提交不可变声明；Bridge 将 `agent.tool_use` 事件和关联的沙箱执行任务作为单笔事务写入 PostgreSQL。
3. **沙箱按需激活与执行**：沙箱服务的工作节点从队列拉取该执行任务。如果该会话此前尚未分配计算机，或者已有计算机处于休眠状态，沙箱服务先触发延迟激活机制（创建微虚拟机、配置网络并挂载所需工作区文件），随后再执行命令并将运行输出写回数据库，标记为已完成但未消费。
4. **结果消费与状态闭环**：运行时收到结果就绪通知，向 Bridge 发起 `agent.tool_result` 声明。Bridge 在单笔事务中同时追加结果事件、将内容投影到模型上下文表、将沙箱结果标记为已消费，并返回幂等回执。只有收到该事务确认后，运行时的状态机才允许推进到下一个推理步骤。

## 当前限制与未决问题

1. **基础设施编排与容量反压尚不完备**：在原型阶段，调度层尚未建立基于运行时节点真实负载的容量感知机制；前端接入层、队列堆积压力与下游算力扩缩容之间缺少动态联动，版本滚动发布时由于缺少优雅排空机制，可能导致正在进行的对话轮次被中断重置。
2. **全功能虚拟机的成本与开销依然偏重**：当前对需要文件或命令操作的任务，仍然以完整虚拟机（如 Daytona 实例）作为默认边界。对于单纯的文件读取或只读轻量处理，完整虚拟机的冷启动和驻留资源仍然显得过重，未来需要结合虚拟文件系统或轻量隔离沙箱进一步细化分级。
3. **长期状态膨胀与存储扩展性**：长程任务会产生海量事件流与执行轨迹，单纯依赖单一关系型数据库的主从模式在超大规模场景下必然面临写入和索引瓶颈。如何在保证事务提交一致性的同时，对冷历史数据执行归档与向量化检索，仍需进一步探索。
