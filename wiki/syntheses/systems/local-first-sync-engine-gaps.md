# Local-first 同步引擎还缺什么

## 问题

CRDT 库已经能让各端各自修改、最终收敛，为什么真正做一个本地优先应用还是远远不够？一个每天有人在用的产品（Lody）到底需要同步引擎额外解决哪些问题？

## 简答

CRDT 库覆盖的是纯计算那部分：结构化文档建模、合并、增量同步、更新可以安全重发。网络、本地持久化、同步协议、跨流事务、鉴权、端到端加密、去中心化下的交互设计，以及「谁来付钱」，都不在 CRDT 库里，需要同步引擎这一层补上。讲者（陈志轩，Loro 作者）用 Lody 的落地过程逐项说明了这些缺口长什么样。

## 来源事实

这一节只写视频里讲到的内容，方括号里的时间戳对应 `raw/sources/local-first-sync-engine-talk.md` 中的段落。

### 本地优先的承诺与能力边界

- 讲者对本地优先的定义是：用户控制数据，可以自由切换云端作为备份，云端只是备份和额外副本，不是权威所有者。和 Local Only 的区别是仍然保留多设备同步的便利。[00:00]
- 他列出的五种体验是：秒开（数据读写都在本地）、离线可用、多端协作、后端可以切换、数据归用户所有（服务商无法把用户挡在软件之外，也不能随意读取数据）。[01:54]
- 最接近这个理想的现成例子是 Git：用协议定义本地和远端怎么交换数据，可以换后端（GitHub、GitLab、自建）。缺的是一个大众级应用来完整交付这种体验。[02:31]
- 他引用 Martin Kleppmann 在 Local-first conference 的分享来描述社区对同步引擎的期待：开发者不用再操心请求失败、超时、数据有没有到服务器、怎么在前端告知用户，这些都交给同步引擎。[03:01]
- 能力边界：强一致场景（抢票、库存管理、支付、会议室抢占预约）原理上做不了；最终一致的场景（代码、视频剪辑、音乐创作这类创作工作）可以统一解决。[04:00]

### CRDT 库已经提供和没有覆盖的部分

已经提供：[05:15]

- 像 JSON 一样建模结构化文档；
- 最终一致性，各端拿到相同的更新集合就得到相同状态；
- 增量同步；
- 文本、列表这类合并结果尽量符合预期；
- 更新可以安全重发，不会被应用两次。

没有覆盖：[06:23]

- 网络层、持久化层这类 IO；
- P2P 环境下的具体做法；
- 同步协议怎么设计（目前比较百花齐放）；
- 去中心化环境下的鉴权和交互设计。

讲者的总结是：这些库本质上是很纯的状态计算，不含 IO。

### 用 Lody 反推出来的六件事

1. 目录和内容要分开同步（Flock）。文档级 CRDT 只能同步单个文档，要同步整个 repo 时就得自己组合别的办法。[07:38]–[09:19] Lody 为此自研了 Flock：它同步的是「有哪些文档、有哪些行和 metadata」这份目录，用户点进具体文档时才拉正文，这样打开应用不需要全量加载。Flock 的存储格式迭代过三次：简单 JSON 很快撑不住，V1 二进制格式受 SQLite 原地更新方式启发、设计过度复杂容易出错，V2 改成受 KV 存储启发的格式，性能和稳定性都更好，切换过程用户没有感知。讲者说 Flock 之后会开源。
2. 本地存储放哪里。[09:51]–[10:23] Web 上试过 SQLite + OPFS：浏览器每个 Tab 是独立的，而 SQLite 只能有一个 writer，多 Tab 就要抢这个写入权限，架构上得先选出一个 leader 来持有 SQLite 并负责所有写入，整套非常复杂，当时也没有现成的开源方案，最后换成了 IndexedDB。
3. 本地全文搜索。[10:57]–[11:31] 云端很容易，直接用 Elasticsearch 或者 Postgres 的全文搜索插件；本地则要同时处理懒加载（不能一打开就全量加载）和端到端加密，这部分当时还在尝试。他猜测将来可能用语义化搜索，并尝试和加密手段结合。
4. 预加载和 Metadata First。[11:31] 反复迭代过的点是：既要尽量用满前端的网络和性能，又不能出现「对话有更新、点进去还要再等」，要把先看到的信息提前同步好。
5. 本地的性能开销。[12:10] 复杂度从云端挪到本地之后本地有额外开销，一部分计算要移到 Web Worker 上做，这部分当时还没解决。
6. 跨流没有事务。[12:51]–[14:06] 发一条消息其实是两个动作：更新 Flock 里那篇目录文档（表现为有新消息），以及写入真正的消息正文。两个流之间没有事务性，发送或接收时任意一条流断开，就可能出现「提示有新消息、点进去看不到」。再加一个 CRDT 也解决不了，这是同步引擎该提供的能力，目前只能在建模和时序上绕开。

### 云端：从 Cloudflare Durable Objects 换到 Durable Streams

先解释了为什么要做云端：大部分用户想要开箱即用的托管服务，同一协议下既可以有不同托管后端也可以自建，这并不违背本地优先，GitHub 就是成功的例子。组织和权限这些东西也变成开箱即用。[15:13]

第一版用 Cloudflare Durable Objects 直接管一个 repo，很快发现承载不了：[15:37]–[17:46]

- 做版本比对要么把更新都拉出来加载进 CRDT 文档，内存和读取开销都很高；要么把版本信息存在 Durable Object 自带的 SQLite 上，每次更新都要更新版本 vector，读写成本也不低；
- 一个 repo 内还有不同权限（只读、可写、某些 room 只对部分人开放），成本更高；
- Durable Object 按 WebSocket 连接时长计费，要省钱就得进 hibernation 释放内存，但释放后所有状态只能写回自带的 SQLite，成本又转移到 SQLite 读写上。

他说这里最反常的地方在于：CRDT 本来让服务端只需要当中转，聪明的客户端就能把冲突合并算完（不像 OT 需要在服务端算），但 Durable Objects 这套用法逼着服务端做很多计算、还占内存。[17:46]

换到 ElectricSQL 的 Durable Streams 协议并自己实现后端之后：[18:28]–[19:32]

- 每个 stream 对应一个 URL，像一个 append-only file；
- 被 push 进来的更新可以广播出去；
- 客户端拿 stream 上的一个 offset，就能取到 offset 之后的所有更新，用来给 CRDT 做 catch up；
- 需要保存的状态最少，服务端只要提供流式日志这种能力，客户端本地只存一个 offset。

在 Durable Streams 之上又做了三处扩展：[20:04]–[20:34]

- 客户端可以发布 snapshot：bootstrap 时直接从快照起步再追尾部。只拿更新会残留一些比较难压缩的 metadata，而某个节点之前的更新做成快照可以压得很小；
- Ephemeral Channel：光标、在线状态这类同步；
- append CAS：给端到端加密用的原语。

端到端加密加在客户端，服务端不需要做什么改动，所以后端即使被攻破，攻击者也拿不到数据、没法伪造数据。[21:08] 局限是鉴权目前还是中心化的：去中心化鉴权方案（提到的 Beehive 之类）还比较 Alpha，没有稳定可直接用的协议，端到端加密本身也还是基于服务端的线性日志。

云端整体架构是：客户端到网关做完鉴权，背后每个 stream 落到一个 Raft group，热存在这个 group 的机器上，冷存落到对象存储。[21:44]

效果上，用了本地优先架构之后加载快（数据一直在本地）、同步快（增量同步交给 CRDT 自动处理），端到端加密是还在推的功能。[22:19]

### 商业模式

他提到这是本地优先同步引擎最容易被忽略的难点：过去几年做本地优先的团队很多被 acqui-hire 收走，对应的托管服务下线，他举了 Electric 和 InstantDB（这一条是讲者的说法，本次没有独立核实）。[22:55]

原因他归纳为：本地优先模式还太新，前面的开放问题太多，没有很完整的解决方案；即使有团队出售方案，采购方适配成本高、会消耗创新预算，所以很难发生重采购；只卖一个模块又只能卖给小范围爱好者，做不出大单。infra 生意通常要等客户端需求暴增才成立，本地优先还没等到这样的场景。[23:36]

他认为下一波机会可能在本地 AI：大模型可以在本地推理之后，个人、家庭和小组织这些场景会有更多需求。[24:14]

结尾他把缺口收成一句话：鉴权、端到端加密、跨端的事务性、去中心化的 UI/UX，以及商业模式。[24:52]

## 综合结论

按「谁负责哪一层」把视频里的问题重排一遍：

1. **CRDT 库负责纯计算**：合并、增量、幂等重发都在这一层，覆盖的是最终一致场景。强一致场景（库存、支付、抢占式预约）原理上不属于它，也不该指望它。
2. **IO 和运行时需要另外设计**：本地存哪里（浏览器多 Tab 抢单个 writer）、目录怎么同步（Flock 这类目录 CRDT）、预加载策略、把重计算挪到 Web Worker。这些在 CRDT 库里都没有对应物。
3. **协议层的正确形状是流加游标，不是「服务端帮你算」**：append-only stream + offset 让客户端自己 catch up，再补 snapshot、ephemeral、CAS 三类扩展就够用。服务端做复杂合并是这套设计里的错误方向——CRDT 已经把计算交给了客户端，服务端再算一遍只会同时抬高内存、读写和连接计费成本。
4. **有些问题加 CRDT 解决不了，属于同步引擎的职责**：典型是跨流的事务性。目录流和内容流要么一起生效、要么都不生效，在协议没有提供之前，应用只能靠建模和时序规避，代价是 UI 上出现概率性的不一致提示。
5. **机密性和权限要分开看**：端到端加密可以只加在客户端，服务端继续当中转、只处理字节；但鉴权仍然依赖中心化的线性日志。去中心化鉴权还没有稳定方案，讲者选择了务实的路线。
6. **商业模式决定了上面这些能力有没有人长期维护**：本地优先 infra 目前没有稳定收入模型，团队容易被收购、托管服务随之下线，这既是生态问题，也是选用托管后端时的实际风险。

## 对个人或项目的启发

- 选型时不要把 CRDT 等同于同步引擎：先问清楚 IO、协议、事务、鉴权、加密分别由谁提供，缺的部分是自己补还是先绕开。
- 目录和内容分开同步，先同步「有哪些东西」的元数据，再按需拉正文，避免启动即全量加载。
- 服务端越薄越好：append-only 日志加 offset 就够，合并留给客户端。
- 端到端加密设计成客户端自己加，服务端不必为它改协议；前提是接受鉴权仍然中心化。
- 跨流一致性要在建模阶段就设计规避方案，不要指望再加一个 CRDT 自动解决。
- 浏览器里做本地存储，不要默认 SQLite + OPFS 能直接跑通，多 Tab 抢单个 writer 的问题要先想好选主和写入路由。

## 待确认和已知限制

- 去中心化鉴权没有可用路径：视频只提到 Beehive 一类方案仍是 Alpha。
- 本地全文搜索和端到端加密怎么结合：只有「可能是语义化搜索」的猜测，没有落地细节。
- 跨流事务：视频只指出问题，没有给出同步引擎侧的解法。
- 「语义化搜索」这一处来自机器转录（原文为「余一化搜索」），没有和讲者确认。
- 商业模式部分（Electric、InstantDB 被收购，服务下线）是讲者的说法，本次未独立核实。
- 视频开头列出的五种体验中「数据归我所有」同时包含不被服务商屏蔽和隐私两层含义，讲者没有进一步区分。
