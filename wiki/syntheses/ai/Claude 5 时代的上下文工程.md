# Claude 5 时代的上下文工程

## 问题

当模型已经能根据代码库、工具接口和用户意图做出较成熟的判断时，系统提示词、`CLAUDE.md`、Skills、memory 和任务参考物应该如何分工？过去依靠堆规则、堆示例和重复强调形成的护栏，是否仍然有效？

## 简答

上下文工程的目标不再是“尽可能多地告诉模型”，而是让每类信息只出现在正确的层级，并在正确的时机加载。稳定的身份与安全边界留在系统层；仓库特有的 gotchas 留在 `CLAUDE.md`；任务型知识和工作流进入按需加载的 Skills；个人偏好与历史事实进入 memory；当前任务的精确要求通过代码、测试、原型和 rubric 等高保真 references 提供。

规则仍然需要，但应优先保留不可推断、不可协商、出错代价高的约束。重复、过时、互相冲突或模型可从环境直接判断的规则，会消耗上下文并降低决策清晰度。

## 来源事实

Claude Code 团队披露，面向 Claude Opus 5 和 Claude Fable 5 等新模型，他们删除了系统提示词的 80% 以上，在内部 coding evaluations 上没有观察到可测损失。团队认为，旧提示词中的许多强约束曾用于压制旧模型的最坏行为，但新模型已有能力根据周边代码、用户偏好和任务语境做判断。

团队还观察到，系统提示词、Skills、`CLAUDE.md` 与用户请求之间经常出现重叠甚至冲突。模型通常仍能得出合理结果，但必须额外判断哪条指令更适用。为此，Claude Code 把代码审查、验证等内容拆入独立 Skills，并使用 deferred loading，让非当前任务所需的信息不提前占用上下文。

## 综合结论

### 1. 上下文应按职责分层，而不是集中堆放

| 层级 | 适合承载的内容 | 不适合承载的内容 |
| --- | --- | --- |
| 系统提示词 | 产品环境、Agent 职责、权限与安全边界 | 具体项目的长篇操作手册 |
| 仓库指令 | 仓库用途、特殊约定、隐藏 gotchas | 文件树可直接看出的常识、个人记忆 |
| Skills | 特定任务的知识、流程、边界和验证方法 | 每次请求都必须加载的基础身份 |
| 工具描述 | 参数语义、状态约束、调用边界 | 与工具无关的全局行为要求 |
| Memory | 用户偏好、历史决定、长期事实 | 当前任务的完整规格 |
| References | 当前任务的代码、测试、原型、规格和 rubric | 长期全局规则 |

信息放错层级会产生两种成本：一是每轮都为暂时用不到的内容付出上下文成本；二是同一要求在多层复制后逐渐不一致，形成隐性冲突。

### 2. 从“规定每一步”转向“定义判断边界”

旧模型常需要类似“永远不要写多行注释”的强规则，以避免常见失败。但这种规则对部分任务必然错误。更稳妥的写法是要求模型匹配周边代码的注释密度、命名和惯例，把决定权放在可观察的项目上下文中。

这不意味着取消硬规则。外部发布、现实资金、删除数据等授权边界，隐私与凭据禁令，不可逆操作前的确认要求，以及模型无法从环境推断的关键工程 gotchas，仍适合明确写死。

判断标准不是“规则越少越好”，而是：缺少这条规则时，模型是否会稳定犯错；违反后果是否足够严重；这条规则是否在当前层级具有唯一权威。

### 3. 好接口比大量示例更能泛化

示例会告诉模型一条可行路径，也可能把探索空间锁在示例附近。对能力更强的模型，应优先通过参数名称、类型、枚举、状态机和不变量表达意图。例如状态枚举与“同时最多一个任务处于进行中”的约束，本身就定义了工具的行为模型。

示例仍有价值，但更适合展示反直觉 gotcha、失败边界或难以从类型表达的协议，而不是重复显而易见的基本调用。

### 4. 渐进式披露是控制上下文成本的核心机制

验证、代码审查、部署、故障处理等知识可以拆成独立 Skill；大量工具可以先只暴露名称和用途，需要时再加载完整 schema；长 Skill 可以用 `SKILL.md` 做路由入口，把细节放入 references、scripts 和 assets。

有效拆分必须保证：

- 入口描述足以让 Agent 判断何时加载；
- 细节文件有明确路由，不要求 Agent 盲目遍历；
- 不可违反的边界不会因为延迟加载而缺席；
- 同一权威规则不会在多个文件中复制。

### 5. 高保真参考物正在取代低信息密度说明

复杂任务里，与其用长篇自然语言描述目标，不如给模型可直接验证和执行的参考物：测试套件表达行为规格，现有代码表达惯例，HTML 原型表达界面结构，rubric 表达验收尺度，参考实现表达迁移目标。

自然语言仍负责说明意图和取舍，但代码与可执行验证通常能减少歧义。参考物的价值不只在“信息更多”，而在于它们能参与验证。

## 对现有 Agent 系统的审计方法

1. 列出系统提示词、仓库指令、Skills、工具描述和 memory 中的全部要求。
2. 标记完全重复、语义近似和互相冲突的条目。
3. 对每条要求追问：模型能否从代码、工具 schema 或当前环境直接推断？
4. 把任务型流程下沉到 Skill，把个人事实迁移到 memory，把工具规则归还工具描述。
5. 为安全红线、外部动作和高代价错误保留明确的上层约束。
6. 用真实任务做回归评测，确认精简没有损害关键行为。

精简的评价指标应包括：上下文 token、指令冲突数量、Skill 误加载率、关键任务成功率、高风险边界违规率，以及失败后能否定位到唯一权威规则。

## 风险与边界

- “系统提示词减少 80% 且评测无损”来自 Claude Code 团队的内部经验，原文未公开完整评测细节，不能直接外推到其他模型、领域和工具环境。
- 弱模型、轻量模型和高随机性场景可能仍依赖更多显式步骤与示例。
- 自动记忆会引入错误写入、过期事实、隐私和召回污染问题，不能把治理责任全部交给自动机制。
- 渐进式披露依赖可靠路由；如果 Skill description 或工具搜索不稳定，关键知识可能没有进入上下文。
- 过度简化可能把“冲突”变成“缺失”。删除规则前必须用真实失败样本和回归评测验证。
