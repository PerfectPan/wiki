# Wiki 页面类型与写作参考

整理来源、选择页面类型或修改正文前读这份参考。目录、frontmatter 和命名遵循仓库根目录的 `SCHEMA.md`，收录索引另见 [资源收录标准](resource-catalogs.md)。

## 先确定这页要回答什么

| 类型 | 读者来这里做什么 | 应保留的内容 |
| --- | --- | --- |
| raw | 回查判断依据 | 来源版本、核查位置、观察结果、未测试项 |
| topic | 理解一个对象或概念 | 本质、核心数据流、工程限制 |
| synthesis | 学会可以复用的做法 | 具体业务例子、通用方法、适用条件 |
| comparison | 为具体需求选方案 | 路线差异、选择理由、代价与评测前提 |

按用途分工，不按篇幅或来源数量分类。同一个对象不必同时生成四类页面，也不必同时建 raw 和 topic。

## raw：回查证据的底稿

新写的 raw 记录只保留三类信息：

- **访问元信息**：来源地址（URL）、访问日期，以及源码提交版本（commit）或资料版本。
- **核查证据**：在哪个文件、函数或代码行读到了什么。源码链接固定到 commit，并标出行号。网页记录具体章节，避免只贴首页链接。
- **未测试项**：哪些行为只读过代码或文档，哪些场景没有实际验证。

每条证据写清观察到的事实。代码里有重试分支，可以记录这个分支，不能据此声称已经通过故障恢复测试。

面向读者的完整机制说明、大段文章和架构图放 topic，不在 raw 再维护一份。一两句话就能说明用途和限制的资源，直接附来源收录，不建 raw。

已有原始材料按 `AGENTS.md` 的保留规则处理，不因新增写作参考而批量覆盖或删除。

## topic：解释一个对象或概念

一页围绕一个工具、框架或独立概念展开：

1. **第一句说清本质。** 软件对象说明运行在哪个进程、由什么组件实现、主要做什么。概念页先给准确的定义和适用范围。使用具体事实，不复述官方宣传词。
2. **画清一条核心数据流。** 跟随一次请求或一个输入，说明谁接收、怎样处理、写到哪里、最后返回什么。图中每个组件和箭头都应有依据。
3. **写清工程限制。** 分别说明做不到什么、依赖什么环境、失败或重启时会丢失什么。不要只写“存在兼容性问题”或“需要注意风险”。
4. **在结论旁附依据。** 让读者能从关键机制和限制回查到文档章节或源码位置。

例如，软件介绍可以这样开头：“这是一个本地 Node.js 进程，通过 HTTP（超文本传输协议）接收事件，并将记录保存到 SQLite。”这类句子交代运行位置、入口和存储，比“新一代智能基础设施”更有用。具体技术名必须来自所读资料，不能照抄示例。

## synthesis：总结跨方案的通用做法

用一个业务问题贯穿全文，再从不同实现中提炼方法。不要依次罗列各家的功能，最后补一句笼统总结。

例如，讨论记忆修订时，可以一直围绕“用户把项目 A 的包管理器从 npm 改为 pnpm”展开。结论按动作顺序写：

1. 保存这次纠正的来源，并限定它只适用于项目 A。
2. 替代旧记录，同时更新由旧记录生成的索引。
3. 下次召回前检查有效性，确认不会继续采用旧约定。

每一步说明采用这个做法的原因、实现依据和适用条件。分开标明来源已实现的行为与本文提出的设计建议。

## comparison：帮助读者做选择

先用一段短文或并列列表概括各方案的本质路线。写清它们分别把工作交给谁、在哪里运行、用什么保存数据，让读者先知道差异在哪里。

再按业务需求给出选择表：

| 如果需要 | 优先选 | 因为 | 需要承担的代价 |
| --- | --- | --- | --- |
| 具体需求 X | 方案 Y | 直接满足 X 的机制 Z | 运维、成本或能力限制 |

每一行都要能用于判断选择。避免只把功能数量、星数或宣传形容词排在一起。

引用跑分时交代：

- 测的是什么指标，例如检索命中率还是最终回答准确率。
- 使用什么数据集、模型、配置和硬件条件。
- 是否用了额外重排、模型调用或人工处理。
- 数据来自谁，本次是否复现。

条件不同的成绩不直接排序。尚未核实的前提明确写出，不将产品宣传当作本次验证结果。

## 配图选择与核对

- **先确定图要解释的问题。** 对照已读源码或资料列出组件、关系和关键条件，再选形式；架构图不能只把 README 的功能列表画成方框。
- **有可用生图工具时，概念解释、模块架构、系统边界、入门对比和生命周期概览优先考虑 imagegen / image_gen。** 没有生图工具时使用 Mermaid 等已有能力，不为配图自动安装或接入新服务。用户指定形式时按用户要求执行。
- **流程图可以继续用 Mermaid。** 需要逐项核对的接口时序、状态转换、条件分支或精确依赖关系，也优先使用可直接修改节点和连线的 Mermaid；不要仅因内容技术性强就把所有图都画成 Mermaid。
- **在本次修改范围内逐张评估已有图。** 根据可读性、准确性和维护成本决定是否换成生成图片，不批量替换全库；同一信息保留一张清楚的图即可。
- **生成后必须看图核对。** 风格尽量沿用参考站点或同页配图。逐项检查文字、箭头方向、分组、条件、数值和技术含义；发现错误先修正，未核对的图片不进入页面。Mermaid 也要核对关系与代码块，能渲染时检查渲染结果。
- **正文保留解释和来源。** 图片放在 `raw/assets/`，使用仓库内链接，不让图片成为唯一技术依据。默认只保存实际使用的图片，用户要求复现资料时再保存生成提示词或记录。

## 通用行文规则

- 第一段先给定义或结论，让读者知道这页解决什么问题。
- 少用分号串联多个判断。有先后顺序的动作写成有序列表，并列维度或条件写成无序列表。
- 一条列表围绕一个动作或判断展开。简短、连贯的解释仍用段落，不把每句话都拆成一条。
- 英文缩写首次出现时注明中文含义。例如 ACP（Agent Client Protocol，agent 与客户端的交互协议）。保留 top-k、Zod 等准确术语，不因它们是英文就判为黑话。
- 直接写具体对象和动作，不用比喻造词。“按类别管理”比“分轨”更清楚。
- 请求、响应和字段用“接口定义”，双方交互要求用“调用约定”。
- 没运行过的测试写“未测试”。只读过测试代码时写“已读测试代码，未测试”，不能写成“测试通过”。运行过则记录命令、结果和覆盖范围。
