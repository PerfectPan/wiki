# Agent 主动上下文管理

## 问题

长对话、多分支探索和长期个人助手场景里，agent 不只需要“把相关资料放进上下文”，还需要能判断哪些上下文应当保留、压缩、卸载、恢复或回溯。现有的 compact 往往把问题推迟到上下文窗口快满时才处理，容易丢信息，也不够任务感知。

## 简答

更合理的方向是把上下文看成一种可被 agent 操作的结构化状态：agent 在任务过程中主动标记关键节点、查看上下文骨架、在必要时带 summary 跳转到历史节点，并保留回到未来分支的能力。这样上下文管理从“被动压缩”变成“生命周期管理”。

## 综合结论

- 当前很多上下文管理方案重心在检索和注入，比如 RAG、memory 或文件读取；但长期任务真正容易失控的部分，是上下文累积后的清理、分段、恢复和接力。
- 阈值式 compact 是必要兜底，但不应是唯一机制。它通常在窗口接近上限时触发，调用成本高，且容易把任务结构、失败路径、约束和用户偏好压扁成一段不够可操作的摘要。
- agent 理论上更适合在语义边界上主动处理上下文：读完一批文件、完成一轮实验、确认某个方案失败、切换到新话题、开始新分支时，都比“窗口快满了”更适合作为 checkpoint。
- `session tree` 提供了一个比线性聊天记录更合适的抽象。每条消息是节点，多线探索自然形成分支；如果每个分支的结果被压缩为 summary 节点，主线就能保持干净，同时保留回溯能力。
- 用 Git 类比有助于把设计讲清楚：
  - `tag` 标记关键上下文节点；
  - `log` 展示当前会话骨架；
  - `checkout` 跳到某个历史节点；
  - summary 类似 merge commit，保留结论而不是保留全部过程噪音。
- 这类机制必须面向 agent 暴露为工具，而不只是面向人类的快捷键或 UI。否则 agent 仍然只能被动等待人类手动整理上下文。
- 一个可用的 `context_log` 不应只是列出所有消息，而应提供上下文仪表盘：上下文占用率、当前分段长度、最近 tag、关键 summary、最近未折叠消息，以及必要时展开历史片段的入口。
- `context_checkout` 的关键不是单纯回到过去，而是带着经过压缩的消息回去。它像 d-mail：把“未来分支已经试过什么、结论是什么、应该避免什么”发回过去节点。
- 更完整的系统还要支持回到未来。否则每次回溯都可能丢掉后续探索的资产。可行做法是在 summary 中记录来源节点或分支关系，让 agent 能在历史节点之间无损穿梭。
- 对 coding agent 来说，上下文回溯还要和文件状态、git 状态区、工作区快照区分开。模型上下文回去了，不代表文件系统也回去了；如果这层边界不清楚，agent 会把过去的推理状态和未来的文件状态混在一起。
- 对个人助手来说，这类机制比一次性 coding 任务更重要。长期助手会持续跨话题、跨项目、跨日期积累上下文，需要能在任务线之间跳转，而不是把所有历史混进一个不断膨胀的聊天窗口。

## 可落地的设计要点

- 提供 `context_tag`：让 agent 在任务关键节点主动打标签，例如 `plan-done`、`source-ingested`、`try-a-failed`、`wiki-pr-opened`。
- 提供 `context_log`：输出可消费的上下文骨架，而不是完整聊天历史；必要时支持按节点展开原始消息。
- 提供 `context_checkout`：允许 agent 跳回某个节点，并携带结构化 summary，说明当前分支的发现、失败原因、保留事实和下一步建议。
- 把使用规则写进 skill 或系统级操作规范：什么时候打 tag、什么时候查看 log、什么时候 checkout、checkout summary 应包含哪些字段。
- 将上下文 checkpoint 与外部状态区分建模：模型上下文、文件系统、git branch、运行中进程、外部发布动作都不是同一种状态，不能用一次 checkout 模糊处理。
- 对长期任务保留轻量 HUD：上下文占用、最近 checkpoint、当前任务阶段、是否存在未总结分支。

## 风险和未决问题

- 过度打 tag 会产生新的噪音。上下文骨架本身也需要折叠、筛选和维护。
- 每轮都生成全量 session log 成本会过高，需要找到合适触发点，或让 agent 在当前会话内增量维护骨架。
- 跳转决策本身可能出错。agent 可能因为误判而回到错误节点，导致丢失最近有效上下文。
- 文件状态和上下文状态同步很难。尤其是 coding agent，一旦回溯推理但不回滚文件，必须明确告诉 agent 当前文件仍处于哪条时间线。
- 这种机制是否真的提升长任务质量，需要在真实个人助手、代码维护、deep research 和多分支调研任务中验证。
