# Plan Mode 的失效边界与人类理解问题

## 问题

“先出计划、批准后再执行”这类工作流还有多少价值？如果一个产品把计划做成一等公民却失败了，失败的是计划本身，还是承载计划的那个界面？

## 简答

Ayman Nadeem 的复盘区分了 plan mode 的两个用途：为 agent 提供足够精确的指令，以及帮助人理解系统。按他的观察，前者随着模型能力提升而减少，后者仍重要；Nuanced 把规划固定为长 spec 和串行审批流程，没有达到预期。

wangleineo 的[知乎补充](https://zhuanlan.zhihu.com/p/2087525914590573749)把问题进一步分成 Spec、Defaults 和 Gap：工具应重点发现那些 agent 已经决定、用户尚未理解但需要参与的事项，而不要求人检查所有实现细节。这也意味着文档仍可用于解释关键变化、保留已认可的行为要求，不能从一次产品失败推出所有计划文档都无用。

## 来源事实：Nuanced 的失败复盘

### 产品想解决什么

- 作者观察到 AI 把代码产出速度和体量拉高，但支撑这种节奏的界面没跟上，于是围绕“计划”做了一个桌面编码应用 Nuanced。
- 它要回答的问题，原文表述是：当机器改代码的速度超过人检查的速度，人怎么维持对系统的连贯心智模型。
- 具体形态：thread 即对话；系统主动把“需要你拍板的歧义和决策”翻出来；谈成一个持久计划后再实现，并尽量让代码符合需求。目标是一条从意图一路到实现、评审、验证的流水线。作者把它定位成“人脑的假肢”，既用来指挥，也用来帮自己盯住进展。
- 他描述的痛点很具体：架构留白会被 agent 自行填充，它划出来的抽象边界之后会变成麻烦；误解和错误的假设会沉到 chat 表面以下的很多文件里，很难被翻出来。用他的话说，这种状态下自己像“僵尸”，尤其是开始并行跑多个 agent（Conductor、Codex）之后，既聚焦不了也验证不了结果；也没有一条可解释的轨迹串起 prompt → agent 决策 → 代码 → 产品行为。

### 用户不买账的四条原因

1. **把 planning 和 plan 混为一谈。** 他假设“先充分想清楚、再把这部分思考保存成结构化产物”有价值，但早期用户对这份 spec 几乎没有胃口。
2. **模型变强了。** 模型靠上下文和记忆理解大仓库的能力提升后，探索仓库、做合理假设都变得可靠，“必须显式交代”的部分缩小了。作者承认自己原先没把模型能力和“给人设计更好的思考界面”看成竞争关系，但两者确实在竞争：**模型能可靠自己做的决定，就是一件不必再摆到人面前的决策**。
3. **没人愿意读 AI 生成的文本。** spec 的信息量变大了，清晰度没有——文档太长，而且“AI 生成文本的节奏和过度结构化的写法让人很难读，眼睛一直发直”。他们的补救是再做一层 Spec Tour，带用户走一遍重点；结果只是又叠了一层注意力负担。作者的反问是这一节的关键：如果必须生成 spec 的短表示才能让 spec 可用，那整份文档一开始是干什么的？
4. **把一个本该连续的过程切开了。** 流程是 chat → 消歧提问 → 生成 spec → 评审 spec → 修订 → 批准 → 实现 → 评审代码。但真实思考不长这样：先理解一部分、试一下、试出来的结果让你改主意、再试别的，每一步都暴露新问题。这个界面逼用户“提前想完”才能开工；而一旦进入实现，再回到前面的聊天推理就像在流程上倒退。

### 环的形状变了

- 早期值得 `plan → approve → execute`，因为走错方向的代价很高。agent 变强之后，它们能自主行动、自己测自己的活、看过结果再改方案，于是更合适的环是 `understand → act → inspect → clarify → adjust → act again`。
- 作者说他最大的错误是“**把计划变成一件产物，而不是设计一个让人理解得更好的过程**”。规划在环里依然大量存在，只是不必以 “the plan” 这个文档的形态出现。
- 另一个他没料到的负担：plan mode / build mode 的分离让用户先自问“这个任务配不配规划”，再记得用按钮或快捷键切模式。这种区分应该由已经有上下文的 AI 来判断。
- 他对这条的自我调侃是 midwit meme：退回到“聊天界面 + 按需规划”这个最朴素的形态，其实相当好用。

### 他认为仍然没解决的

- 想清楚要建什么、为什么、评估决策，依然重要；人也依然需要连贯的心智模型。但一大坨 AI 生成的文本不是合适的界面。
- 难的地方是“随着系统变化，理解怎么保持最新”，而且从 5 个 agent 到上百个只会更难。“跟上”不可能等于读每一段对话、给每一次代码改动要一段解释。
- 他的判断是：agent 需要找出**人的注意力能产生最大影响的少数位置**，并把足够的上下文端到那里。
- 结尾的立场：界面会随技术一直变，但“把复杂性变得可理解”这个需求不变。

## 知乎补充：Spec、Defaults 与 Gap

以下分类来自 wangleineo，而不是 Nadeem 原文。两篇文章关注同一个问题，但补充文章把“人需要理解什么”说得更具体。[来源阅读摘记](../../../raw/sources/2026-09-28-zhihu-plan-mode-insights.md)

| 分类 | 作者表达的含义 | 区分它的关键 |
| --- | --- | --- |
| Spec | 用户和 agent 都知道的设计与技术决定 | 双方已有共同理解，可以记录下来 |
| Defaults | agent 知道、用户无需关心的实现选择 | 用户不在意在可接受范围内选 A 还是 B |
| Gap | agent 已决定，用户不知道但应该知道的事项 | 用户如果了解，可能会不同意或作出另一种选择 |

**模型能做出决定，不等于这个决定可以不让用户知道。** Nadeem 关注减少不必要的人工决策；wangleineo 进一步提醒，应区分“执行上可以自主完成”和“取舍已经获得用户认可”。Defaults 可以委托，Gap 则需要暴露相关背景和选择。

作者认为，随着生成速度和自主决策增加，Gap 可能扩大。这是作者的判断，文中没有给出增长量或评测结果，也没有提供自动识别三类信息的算法。

**文档可以服务理解，而不必固定所有实施步骤。** 知乎文中引用了用图和交互演示解释关键变更的讨论，并借《Regenerative Software》提出：能否描述软件应保持的行为，让不同次生成的实现仍符合这些要求。本次没有独立核对所引评论或阅读书籍，因此这里只记录作者提出的方向，不把它当成工具能力或行为一致性的保证。

## 综合结论

- **精确指令与人的理解需要分别评估。** 原文认为模型能独立处理更多实施细节，但这不说明用户对目标、行为和重要取舍的理解也可以省略。知乎的 Defaults 与 Gap 分类补充了这个区别。
- **Nuanced 的失败不能证明持久文档无用。** 这次产品的长 spec 没有让用户更容易理解或决定；仍可保留已确认的行为、约束与决策理由，并在关键变化时更新。篇幅与结构应服务实际阅读任务，见 [[AI Slop]]。
- **摘要是否有用取决于它帮助人做什么。** Spec Tour 在该产品里增加了负担，不代表所有分层说明都无效。应检查解释材料是否让人看清具体改变、备选方案和需要参与的决定。
- **显式模式是元决策负担。** 让用户判断“这个任务值不值得规划”并记得切模式，等于把 agent 本来能从上下文推断的事退回给人。这与 [[Agent 循环工作流的控制边界]] 里“谁来触发、谁来验收”的讨论同向：模式选择更适合交给 harness，而不是做成一个需要记住的按钮。
- **串行 waterfall 的合理性来自“走错方向很贵”。** 当 agent 能自己检查结果并调整方案，这个前提被削弱，规划与执行就自然交织成 loop。这不是“不用规划”，而是规划从阶段变成了环里的动作。
- **按阅读任务组织材料。** 人当场作决定需要相关且精简的解释；后续查证需要可追溯的记录。知识库也不能仅因面向 agent 检索，就容忍重复、冗长或没有依据的内容。
- **“把计划交给人批准”在并行度上升后会失效。** 五个人肉评审五个 agent 的计划还勉强，上百个就不成立。作者给出的方向是 agent 主动挑出少数值得人看的位置，这把问题从“怎么生成计划”转向“怎样识别需要人参与的决定”，涉及工具如何组织信息和触发审阅。

## 对我们的启发

结合上述分类，本页建议先问：**如果用户知道这个决定，他是否可能改变选择？** 这是实践判断问题，不是两篇文章已经验证的检测方法。明确约束内的私有实现细节可以作为 Defaults；改变公开行为、数据处理方式或重要取舍时，应给用户足够的上下文。用户认可后，再记录应持续保持的行为和理由，减少同一事项反复成为 Gap。

- **用具体变化支持审阅。** PR 说明应让人理解目标、影响、来源与验证结果。对于代价高或难以撤销的决定，仍应在执行前确认，不能把“迭代式规划”理解为取消事前讨论。
- **减少不必要的确认，不隐藏重要决定。** agent 可以处理已经授权的实现细节；遇到可能改变用户选择的事项时，应说明备选方案和取舍，而不是只交一份长计划。
- **按阅读任务保留材料。** 当场作决定需要相关且精简的解释，后续维护需要可追溯的行为约束与决策记录。可以使用正文、图或交互演示，但形式本身不保证理解。
- **规划提示词也应说明用途。** 要求先交逐文件计划时，应说明这份计划帮助人决定什么，以及哪些问题可以在实现和验证中逐步澄清，不把产出长计划作为所有任务的默认步骤。

## 未决问题

- 面向人的理解界面到底长什么样？原文只否定了“长文档”，没有给出正解，对话、diff、可运行原型各自能承担多少也还没被拆开。
- 人的理解如何随系统变化保持最新？如果答案不是“每段对话都读”，那么更新的触发点由谁定义？
- agent 怎么判断哪些决定需要用户参与？误把 Gap 当成 Defaults 时，如何发现并纠正？
- 来源限制：两篇文章是一则产品复盘及针对它的评论，不是两项独立评测。Spec、Defaults、Gap 的分类提供了思考方式，但怎样可靠识别 Gap、衡量它是否减少，仍未验证。长期架构决策和跨团队协作中的文档价值也不能据此一概否定。
