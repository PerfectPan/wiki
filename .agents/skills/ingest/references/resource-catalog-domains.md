# 按领域补充 Awesome 收录检查

与 [resource-catalogs.md](resource-catalogs.md) 的通用标准一起使用。先根据 `AGENTS.md` 确定主分类，再选择相关检查；下列项目不是每条资源都必须执行的测试清单，也不要求为所有分类预建索引页。

## frontend

用于组件库、样式示例、渲染与交互相关资源。按收录用途核对：

- 接入现有项目：框架与版本要求、浏览器支持、依赖；涉及服务端渲染时再看 SSR 与 hydration。
- 页面表现：响应式布局、主题与样式覆盖；交互组件再看键盘操作、焦点与可访问性，动画再看减少动态效果的设置。
- 性能与维护：运行时代价、包体或资源加载是否影响使用；复制源码后是否需要自行跟进修复。
- 设计参考：示例能否说明具体效果，代码与展示是否对应；纯灵感或教程按学习价值评审，不把安装测试当成必填项。

例如圆角效果库应检查裁剪对弹出内容和焦点显示的影响；CSS 对照站应看示例适用布局与浏览器支持。演示好看但关键交互未核对时，可以作为参考，不据此宣称可直接用于所有项目。

## 后端服务补充

后端不是当前独立的一级分类。以数据存储、网络、运行时为主的资源通常归 `systems`，以业务组织和服务设计为主的归 `architecture`，以开发、部署、调试工具为主的归 `tooling`。实际归类仍按页面主要内容决定。

资源涉及后端服务或持久化数据时，追加与其职责有关的检查：

- 请求与权限：输入如何校验，身份与资源权限在哪里检查；公开服务是否说明限流或配额。
- 数据与并发：支持哪些事务或一致性保证，并发修改、重复请求、重试会产生什么结果。
- 失败与恢复：超时、取消、重试的条件，写入结果不确定时如何处理；保存数据的工具再看备份、恢复与迁移。
- 运行与排查：部署依赖、配置方式、日志与指标、健康检查、升级条件；性能数字是否交代负载、环境和测试方法。

按具体职责选择：认证库重点看权限与凭据处理，任务队列重点看重复执行与失败重试；不要要求只读开发工具提供数据库事务。缺少关键行为说明的资源可以保留为学习参考，但不据此推荐它承担生产数据或权限控制。

## 其他现有分类

| 主分类 | 领域补充检查 | 什么会影响分级 |
| --- | --- | --- |
| `design` | 面向什么媒介与受众，设计选择怎样解决问题；素材是否可编辑，复用是否需要署名。 | 只有效果图、没有适用场景或做法说明时，不把它当成完整设计方法；灵感资源仍可按参考价值收录。 |
| `ai` | 输出是什么，依赖哪些模型或环境，工具可访问哪些数据；如何验证结果，失败时怎样处理。部署服务时再检查费用与数据去向。 | 仅有演示不能证明稳定效果；准备接入自动化流程时，须核对输出、工具权限与失败处理。 |
| `languages` | 对应语言和版本，示例依赖哪些编译或运行设置，语言特性有哪些限制，迁移影响是什么。 | 旧版本材料可以有学习价值，但应注明版本；实现建议缺少对应版本依据时不直接推荐采用。 |
| `systems` | 资源限制、并发或一致性保证、故障行为与平台依赖；性能结论的测试条件。涉及服务端数据时加读后端补充。 | 演示成功不代表故障下可用；未说明关键保证时只能按已证实的用途收录。 |
| `algorithms` | 问题前提、正确性解释、时间与空间复杂度、边界输入；示例或练习是否帮助理解。 | 只给答案或跑分却不说明条件时，不把它当成完整算法讲解。 |
| `architecture` | 要解决的需求、约束、数据流和依赖，方案为什么这样划分，适用条件与代价；实现后端服务时加读后端补充。 | 只有模式名称或架构图、没有问题与取舍说明时，材料不足以指导采用。 |
| `tooling` | 适用平台与工程环境、安装和集成方式、修改哪些文件或配置、失败后如何恢复。部署工具再加后端补充。 | 会改动项目或系统的工具，缺少影响范围和恢复说明时不直接推荐执行。 |
| `product` | 面向哪些使用者、核心任务怎样完成、费用与限制、数据能否导出，以及权限和第三方依赖。 | 宣传功能与实际可用功能分开；未试用时注明文档评审，不把营销介绍当成体验结论。 |
| `career` | 面向哪个地区、岗位和经验阶段，建议来自个人经历还是可核对的招聘要求，时间是否仍适用。 | 个案不能自动推广到所有地区与岗位；来源过时但仍有参考价值时写明背景。 |
| `life` | 作者背景、适用人群，个人体验与事实依据是否区分；实用建议的条件与时效。 | 涉及健康、法律或财务判断时，核对相应可靠来源；个人体验可作阅读材料，不直接变成通用建议。 |

Agent skill 的具体评审还应参考仓库已有的领域总结 `wiki/syntheses/ai/skill-engineering-artifact-protocol.md`，核对触发条件、交付内容、执行限制和结果检查；本表不替代其中的领域分析。

## 如何影响分级

通用标准和所选领域检查共同支持同一个“推荐 / 可参考 / 偏薄”结论，不按检查项数量机械打分。先说明推荐它做什么，再看与这项用途相关的关键条件是否清楚。

例如，一篇解释重试原理的文章可以因讲解清楚而被推荐阅读；一个实际执行任务的队列库，若没有说明重复执行会发生什么，就不能用相同理由推荐接入业务。分级理由放在对象的原始资料中，不把整份检查清单复制进索引条目。
