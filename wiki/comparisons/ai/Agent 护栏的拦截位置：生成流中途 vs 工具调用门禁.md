# Agent 护栏的拦截位置：生成流中途 vs 工具调用门禁

## 当前结论

两者不是竞品，而是同一护栏设计空间里的**两个拦截点**，按「错误发生后的正确处理是什么」分流：

- 正确处理是**「这事不许发生」**（安全边界：读 `.env`、`rm -rf`、抓坏域名）→ 用**工具调用门禁**（Claude Code permission deny / hooks）：fail closed，硬拒绝，不需要携带「该怎么改」的知识。
- 正确处理是**「这事该换个做法」**（质量纠偏：禁用 API、`as any`、正文里反复出现的错误说法）→ 用**生成流中途拦截**（omp TTSR）：打断 + 注入纠正方案 + 就地重试，把「教会」做在失败发生之前。

harness 设计者应同时提供两档；omp 自己就同时有 Hooks 和 TTSR 两层，印证互补而非替代。

## 备选项

- **omp TTSR（Time-Traveling Stream Rule）**：对流式生成内容做正则 / ast-grep 匹配，命中即打断生成、注入规则正文、重新生成。
- **Claude Code permission deny**：在工具调用提交时（执行前）按工具名 + 参数模式（路径 glob、命令前缀、域名）做硬门禁。
- **Claude Code PreToolUse hooks（≈ omp Hooks）**：工具调用事件上跑外部命令，可阻断并把自己的 stderr 作为反馈注回模型——功能上最接近 TTSR 的既有机制。

## 取舍分析

| 维度 | TTSR（生成流中途） | permission deny（调用门禁） | PreToolUse hooks（调用事件） |
| --- | --- | --- | --- |
| 拦截点 | 生成中途，调用还没写完 | 调用提交时、执行前 | 调用提交时、执行前 |
| 匹配面 | 流式原始文本（可跨 chunk）、助手正文、thinking、ast-grep 源码结构 | 结构化工具输入：工具名 + 参数模式 | 工具名 + 入参（自定义脚本任意检查） |
| 命中动作 | 打断 → 丢弃半成品 → 注入纠正 → 重试；或 `never` 档软提醒 | 硬拒绝，报错返回模型，怎么改模型自己想 | 可阻断 + stderr 注回；或仅观察 |
| 携带知识 | 规则正文即纠正方案（「为什么错、怎么做」） | 不携带，只说不 | 脚本自己决定输出什么 |
| 能否拦 prose / thinking | 能（`text` / `thinking` scope） | 不能 | 不能 |
| 表达「大编辑里任何位置出现 X」 | 天然支持（内容级正则） | 表达不了 | 需脚本自己解析 diff，脆弱 |
| 适用问题 | 惯犯错误的纠偏、约定执行 | 安全边界、不可协商的禁令 | 安全边界 + 自定义策略 |
| 成本特征 | 平时进程内并行匹配，近零；命中 = 作废一次半成品生成 | 每次调用一次模式匹配，近零 | 每次调用起子进程，开销最大 |
| 失控风险 | 误报 → 浪费重试；被「每规则每 session 一次」默认封顶 | 误报 → 无谓阻断 | 误报 → 无谓阻断 |

## 推荐理由

1. **判据是失败后的最优处理，不是机制好坏。** 问一句「这条规则命中后，正确行为是『不做』还是『换做法』？」——前者门禁就够了，deny 的「只说不教」不是缺陷而是本职；后者门禁反而低效：模型拿到一个没有指导的拒绝，多半再错一次，不如在生成中途就把正确方案喂回去。
2. **拦截点越早，失败路径越短，但表达面越受限制。** TTSR 的「流中途」省掉了注定失败的完整生成和工具往返；代价是匹配只能建立在流式文本上，表达不了 deny 那种「按结构化参数精确拒绝」的语义。反过来，deny 的精确性建立在整个调用已生成完毕之上——两个拦截点各拿各的好处。
3. **TTSR 的性能顾虑基本可以排除，但误报是真实风险。** 匹配在本地进程内与生成并行，相比 LLM 延迟可忽略（比 hooks 每次起子进程还便宜）；命中一次的代价（作废半成品生成）小于一次失败工具往返 + 修复回合。真正的风险是规则太宽导致频繁打断——omp 用「每规则每 session 默认触发一次 + after-gap 限频」在结构上封顶，加上 `ttsr scan` 预扫存量代码，属于工程上收敛的问题。
4. **prose / thinking 监听是门禁类机制覆盖不到的能力。** 「模型在正文里反复宣称某件错事」这类错误只存在于生成流里，deny/hooks 的匹配面（工具入参）根本看不到它。这决定了 TTSR 不只是「更早的 deny」，而是覆盖了不同一层的错误。
