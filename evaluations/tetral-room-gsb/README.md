# Tetral 文章整理：三组匿名对照

这次比较 GLM 5.3 独立整理、GLM 5.3 分析与审阅加 Gemini 3.8 Flash 写作、Gemini 3.8 Flash 独立整理三种完整流程。每组从同一个文章 URL 开始，在同一份干净 Wiki 基线上独立抓取、清理原文、分析、写页面、更新已有主题和运行检查。候选编号在生成正文前随机分配，模型对应关系单独保存在本机，等评审完成后揭晓。

这里存放供评审的实验输出，尚未采用到正式知识页。候选文件保留模型完成时的内容，主持人负责归档、检查和组织阅读入口。

## 阅读顺序

1. 先读三个候选的新主题页，判断能否直接读懂、解释是否具体、结论是否有依据。
2. 再看各候选对 Agent Harness 两个已有页面的增量，判断是否补充了可复用知识、是否保留原有上下文。
3. 最后核对各自抓取的原文和检查结果，判断遗漏与噪音是否影响整理结果。

## 共同条件与限制

- 来源：[The Next Scaling Problem](https://tetral.ai/blog/the-next-scaling-problem/)。每组自行抓取，没有预置或共享原文。
- Wiki 基线：`e595104eaf5135287bf282553b87a14a71dd8c03`，未包含此前 Tetral 实验的成稿。
- 三组均通过 agent-room 创建新会话；任务要求和仓库规则相同，工作区相互独立。共同任务见 [task.txt](task.txt)。
- 单模型组负责整个流程和自审；协作组由分析与审阅成员交接给写作成员，允许一次集中返修。
- 协作组返修后达到 Room 默认自动唤醒深度，主持人发了一次“读取返修结果并完成最终复核”的继续指令，没有提供新的内容意见；因此本轮也记录了这项运行介入。
- 比较对象是实际工作流程。各模型使用对应的客户端适配器，协作组的调用次数和上下文也不同，因此不属于工具环境和计算预算完全相同的模型能力测试。
- 每种流程只运行一次、只使用这一篇文章；结果不能证明对其他来源的稳定表现，也尚未验证后续新增来源时的知识整合。
- 完整运行记录、模型对应表和本机连接信息保存在本机，评审包只包含任务、候选内容及必要的检查摘要。
