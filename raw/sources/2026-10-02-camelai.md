# camelAI：文章与两代源码来源摘要

camelAI 的 7 月方案把 Agent 循环、持久文件与 Linux 作业拆开。迁往 camelRun 后，循环改由外部 runtime 执行，Cloudflare 侧仍保留文件、业务工具、构建、分析与发布能力。

## 文章提供的背景

7 月原帖与文章描述了三步迁移：

1. 基于 Pi 底层库自建 harness，将 Agent 循环移入 DO，仍远程调用项目 VM。作者称这一步改善了延迟，但尚未解决每用户 VM 的成本。
2. 去掉项目背后的常驻 VM，将文件放进 DO SQLite/R2，并保留 Artifacts Git 历史。
3. 用 Code Mode JavaScript 和显式方法代替通用 Bash，构建与 notebook 仍使用 Linux 容器。

作者报告成本和延迟下降、小模型使用显式方法更顺利，但没有提供可复现的同条件 benchmark。这些收益属于作者观察，不能当成通用性能或成本保证。

9 月文章说明继续运行长任务时，重启恢复、内存和诊断能力成为问题；随后将 Agent 基础设施迁到 camelRun。该文另外讨论的 D1 事故属于另一个推理项目，不能写成 camelAI 文件数据库事故，也不应据一个案例推断所有 Cloudflare 工作负载。

## 平台限制

- [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)：CPU time 与 wall time 不同；付费 SQLite-backed DO 存储上限 10 GB，单 row 上限 2 MB。
- [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)：128 MB 是 isolate 内存上限，并非每个请求独占预算。
- [DO pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/)：请求、活跃时长、存储分别计费；时长按分配的 128 MB 计，不按实际占用计。多个 DO 可能共享一个 isolate 的内存。

这些限制不能推出所有长任务必定失败，也不能把文章中的延迟与成本观察当作平台保证。
